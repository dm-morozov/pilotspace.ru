# PilotSpace: архитектура и этапы развития

Решение от 27 сентября 2026 года. Офлайн-режим реализован в локальной версии 1.1.0; серверная часть ниже остаётся планом. Публикация проверяется отдельно.

## Текущая версия

HTML/CSS/JavaScript на GitHub Pages. PDF → Python-импорт с аудитом → questions.json/questions.js → тренировки в браузере. app.js объединяет отбор, оценивание, сохранение и отображение. Темы и поддержка вынесены отдельно.

Вопросы имеют стабильные uid, correct_answers и статус verified/needs_review. При новых расхождениях неуточнённые вопросы исключаются из тренировок; сейчас таких нет. verified означает сверку с PDF либо задокументированное исправление его ошибки, а не независимую экспертизу всех авиационных правил. Изменение базы требует повторного аудита.

Прогресс и тема локальные. Ключи chle-progress-v1 и chle-theme сохраняем при смене бренда. Другой домен имеет другое localStorage: автоматического переноса сохранений между адресами нет.

## Порядок работы

1. **Оформление.** Единый знак PilotSpace, favicon, иконки телефона, manifest и мобильная шапка. Manifest задаёт имя и иконки; сам по себе не обеспечивает офлайн-работу.
2. **Сохранения и обратная связь.** Реализованы экспорт/импорт прогресса с проверкой версии банка и подтверждением замены; сообщение об ошибке с uid и страницами PDF через почту. Разбор завершённой попытки добавлен на экран результата: ошибки/все вопросы, правильные варианты, примечания и PDF. Архив завершённых попыток пока не хранится. Логотип возвращает к настройкам без перезагрузки и потери активной попытки. Страница о проекте объясняет источник и ограничения проверки.
3. **Офлайн — реализовано.** Явное скачивание пакета около 8,9 МиБ: интерфейс, вопросы и изображения без полного PDF. `offline.js` управляет состояниями скачивания, `build_offline.cjs` собирает список файлов с SHA-256 и генерирует service worker. Установка новой версии транзакционна относительно прежней; смешанные выпуски, ошибки сети и квоты блокируют готовность. Новая версия ждёт закрытия всех вкладок без `skipWaiting` и `clients.claim`. Первый запуск после скачивания открывается явной кнопкой. Прогресс хранится отдельно в localStorage; кэш браузер может очистить. Порядок сборки и проверки указан в README.
4. **SEO.** Индексируемые страницы реальных разделов, карта сайта и инструменты поисковиков. Аналитику подключать после выбора сервиса и описания фактически собираемых данных.
5. **Разделение кода.** Отделить функции отбора и оценки, модель тренировки, хранилище и отображение. Существующие тесты проверяют сохранение поведения. Стабильные uid не менять ради переработки интерфейса.
6. **Аккаунты.** Один Django-проект, PostgreSQL и Nginx. Django Admin для автора; личный кабинет — страницы приложения. Начать с Django-шаблонов и существующего JavaScript. React не обязателен для аккаунтов или статистики: подключать React/Vite и API при реальной сложности интерфейса. Фронтенд и API обслуживать на одном домене.

## Модель будущей серверной части

Пользователь, версия банка, вопрос с вариантами, тренировка и ответы. Тренировка привязана к версии банка и порядку uid. Сервер рассчитывает баллы сам. Новая база проходит аудит; завершённые тренировки сохраняют связь со старой версией. needs_review остаётся вне оценки.

Первый релиз: вход, история, сохранение тренировки, синхронизация после входа. Перенос гостевого прогресса подтверждается пользователем. Гостевой режим остаётся доступным. Использовать сессии Django, защищённые cookie и CSRF; не хранить токены входа в localStorage. До публичного запуска проработать восстановление доступа, ограничения входа и обработку персональных данных.

Первый серверный релиз синхронизируется при наличии сети и явно показывает статус сохранения. Повторный запрос не создаёт повторный ответ. Сложное объединение офлайн-ответов нескольких устройств отложить.

## Журнал обновлений и будущая доска идей

Журнал уже реализован отдельной статической страницей `updates.html`, доступной без JavaScript. На главной — компактная ссылка и версия. Первая именованная версия — 1.0.0; предыдущие этапы датированы по Git без выдуманной нумерации. Дата записи — дата подготовки; пользователям она становится доступна при публикации. История описывает только реализованные функции, планы вынесены отдельно. Правила выпуска описаны в README.

При переходе на Django достаточно модели Release (версия, дата публикации, заголовок, описание, опубликовано) и редактирования в Django Admin. URL `/updates.html` сохранить или перенаправить постоянно на новый адрес. Отдельный React-интерфейс для журнала не требуется.

Доска идей — после аккаунтов: до трёх открытых предложений на пользователя, один переключаемый голос на идею (свою поддержать тоже можно). Завершённые и отклонённые предложения освобождают лимит. Модели Idea и Vote; уникальность пары пользователь/идея и проверка лимита на сервере, включая одновременные запросы. Статусы: предложено, запланировано, в работе, готово, отклонено. Нужны модерация, ограничение частоты запросов и объединение дублей без повторного подсчёта голосов одного пользователя. Голоса помогают приоритизировать, но не определяют сроки: ошибки базы и надёжность важнее популярности. Готовую идею можно связать с выпуском.

## Развёртывание

Локальная разработка → тестовая публикация → мобильная проверка → выпуск. Сервер арендовать перед тестовым развёртыванием. 1 vCPU / 2 ГБ — начальная оценка для небольшой нагрузки, не обещание числа пользователей. Сборку интерфейса выполнять вне VPS. PostgreSQL сначала на том же сервере. Резервные копии хранить отдельно и проверять восстановление; следить за RAM, диском, ошибками и временем ответа. Микросервисы, Kubernetes, отдельная платная БД и очереди пока не нужны.
